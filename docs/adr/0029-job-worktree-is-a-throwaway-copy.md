# ADR 0029：派工的 worktree 是可丟的副本

- 日期：2026-10-11
- 狀態：已採用（架構審查的第三項，第二部分）

## 背景

派工（ADR 0008、0012）時，OpenCode 在專案的 git worktree 裡工作。裡面的修改要等使用者看過差異、按「套用到專案」，
才會寫進專案；確認的是計畫的內容雜湊，每個檔案寫入時都再經過關卡（ADR 0008 第 6 點）。

政策卻把 worktree 當成專案本身來判斷，所以有幾件事問了不該問的：

- worktree 裡的 `rm -rf build` 被當成危險指令。
- 改 worktree 裡的 `AGENTS.md`、`.github/` 被當成受保護的檔案。這些修改套用前碰不到專案，套用時又會看到差異，等於問了兩次。
- OpenCode 一次改多個檔案（`apply_patch`）時，整個修補被當成一個「外部動作」來問。
  - 模型名稱是 `gpt-` 開頭時，OpenCode 1.18.34 只提供 `apply_patch`，不提供 `edit` 和 `write`，所以每次改兩個以上的檔案都會問。
  - 核准後，這些檔案也沒有記成「核准過的內容」，驗證時被標成「未核准的修改」，工作結果變成「有問題」。

`git push` 原本也沒問。worktree 和專案共用同一個 Git 設定，所以在裡面推送會直接推到你的遠端。
ADR 0028 把所有推送都算成危險指令，這件事已經解決。

## 決定

關卡判斷派工的動作時帶上「這是 job 的 worktree」（`PolicyContext.worktree`）。下面三件事在 worktree 裡直接放行，照樣留紀錄：

1. **遞迴刪除**：每個目標都必須是 worktree 裡的字面路徑。以下情況照樣會問：
   - 目標用了萬用字元或變數：Rocky 把專案的 `node_modules` 連結進 worktree，萬用字元可能碰到連結指向的專案。
   - 目標是一串路徑（PowerShell 的 `a,b`、cmd 的 `,`、`;`、`=`）。
   - 經過連結指到 worktree 外面。
   - 目標是 `.git`，或 worktree 本身。
   - 同一串指令可能先換到別的資料夾：`cd`、`pushd`、`popd`、`source`。`builtin cd`、`eval 'cd …'` 也算，
     因為 Rocky 會拆開它們。`env -C`、`sudo -D` 同理，即使這個程式的「專案外」已經允許過。
2. **受保護的檔案**：worktree 裡的照樣放行，`.git` 除外。worktree 的 `.git` 指向專案的儲存庫，改它等於改專案。
   機密檔照樣會問。
3. **一次改多個檔案**：OpenCode 的修補會列出每個檔案，並對每個檔案附上差異。只要列出的每個檔案都有差異、而且沒有搬移，
   就逐檔當成寫入來判斷，每個檔案各留一筆紀錄，也各自記下核准的內容。
   - 其中一個檔案被拒絕，整個修補就拒絕，前面已放行的紀錄標成「沒有執行」。
   - 有搬移的修補（還會刪掉原檔案，差異裡看不到），或缺了某個檔案的差異，照舊當成一個外部動作；只改一個檔案時也一樣。

其他規則不變：

- 專案外的路徑、讀機密檔、推送照樣會問。
- 等待中的問題被「這個對話都允許」重新判斷時，也用同樣的 worktree 規則。

**限制**

- 「可丟的副本」只對檔案成立。worktree 和專案共用同一個 Git 儲存庫，所以 `git branch -f main`、`git config`、
  `git stash drop` 這類指令在 worktree 裡執行，改的是專案的儲存庫。這些指令沒有放寬，照原本的規則判斷，
  大多不會問（ADR 0019 的輕量護欄）。

## 驗證

| 平台                                       | 指令                    | 結果                                                 |
| ------------------------------------------ | ----------------------- | ---------------------------------------------------- |
| 雲端 Linux，Node 24.21.0，OpenCode 1.18.34 | `npm run check`         | 通過，267 個測試（含真 OpenCode 的派工測試），exit 0 |
| 同上，Playwright 內建 Chromium             | `npm run test:e2e`      | exit 0，27 步                                        |
| 同上，假模型＋真 OpenCode                  | `npm run test:e2e:jobs` | exit 0，10 步                                        |

- 真 OpenCode 的整合測試：模型名稱是 `gpt-5.1` 時，OpenCode 用 `apply_patch` 一次改 `math.js` 和 `AGENTS.md`，
  再跑 `rm -rf build`；只有開始派工時問了一次，兩個檔案各有一筆「成功」紀錄，工作結果是「已驗證」。
  拿掉這次的程式改動，同一個測試會多問兩次（修補和刪除）。
- 每項規則各自做了單獨拿掉的檢查，拿掉任何一項都會讓測試失敗。
- 原本把 `rm -rf build` 當成「會問的指令」的整合測試和派工 e2e，改用 `git push`。CI 不跑派工 e2e。
- 評測裡沒有在 worktree 裡判斷的題目，所以沒有為這部分另外跑評測。
- 沒有在 Windows 上跑過；PowerShell 和 cmd 的規則只用 `path.win32` 判斷過。
