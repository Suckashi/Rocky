# ADR 0035：每一輪只用自己的紀錄和自己的專案資料夾

- 日期：2026-10-12
- 狀態：已採用（架構審查剩下的「現在做」，第六個 PR）；補充 ADR 0022

## 背景

- **研究助手的步驟每一輪都重送給模型。** 研究助手（ADR 0022）的文字、工具呼叫和結果會串流到瀏覽器，帶著
  `subagentRunId`。瀏覽器下一輪把整段對話送回來，`toLangChain` 把它們當成 Rocky 自己的訊息交給模型：每讀一個檔案
  最多 6 萬字，之後每一輪都再送一次。模型原本只看過研究助手的報告（task 工具的結果）。
- **換專案後，進行中的這一輪改用新專案判斷。** 關卡在判斷時才讀「目前的專案」。這一輪進行中使用者打開別的專案，
  原本專案裡的讀寫就被當成「專案外」詢問（或反過來）。
- **評估關卡會在沒有資料時通過。** 基準裡的案例這次每一次都因為提供者錯誤沒有計分時，它不在比較裡，結果仍是
  「沒有案例退步」。

## 決定

1. 送給模型的紀錄略過帶 `subagentRunId` 的訊息；研究助手的報告仍在 task 工具的結果裡。找不到對應呼叫的工具結果
   （研究助手的呼叫被「停止」關閉時，關閉的結果沒有標記）也略過，否則提供者會拒絕整段紀錄。
2. 這一輪開始時的專案資料夾記在 `GateRun.root`；工具沒有指定資料夾時，關卡用它判斷。
3. 評估關卡把「基準有、這次沒計分」的案例列為 `NOT SCORED` 並失敗（刻意略過的案例除外，例如沒有 OpenCode）；
   已經從案例清單移除的，另外列出、不擋。
4. 新增兩輪的評估案例 `research-follow-up`：研究助手查完後再追問，第二輪帶著伺服器為瀏覽器保存的紀錄。第一輪
   必須用到研究助手；第二輪被提供者以 4xx 拒絕算失敗（紀錄是 Rocky 組的），不算提供者錯誤。兩輪各有自己的逾時，
   工具和用量合計兩輪。

## 限制

- 派工的專案仍是排入佇列時的專案，不是這一輪開始時的。
- 新案例還不在基準裡，下次存基準之後才受關卡管制。

## 驗證

- Cloud Linux、Node 24.21.0、OpenCode 1.18.34：`npm run check`（合併 #34–#38 之後 332 個測試，含真的 OpenCode 的整合
  測試）exit 0。
- 實際模型（Command Code `deepseek/deepseek-v4-flash`，ask-when-needed）：
  - 修正前先確認：存下的紀錄裡有 17 則帶 `subagentRunId` 的訊息，之後每一輪都會送給模型。
  - 完整評估 `--repeat 3`：99/99，和基準比沒有案例退步，沒有提供者錯誤。這次執行開始時，還沒有「停止」的修正和
    評估程式的改動。
  - 最終程式碼上 `research-follow-up` 和 `research-with-subagent` 各 3/3。
- 每個修正單獨拿掉後都有單元測試失敗；評估程式的兩輪流程本身沒有單元測試。沒在 Windows 上跑。
