# Rocky 審查附錄（Audit Appendix）

> 本文件是 Rocky 重構計畫的「審查附錄」，可獨立閱讀。內容彙整 13 個獨立稽核區域的完整 JSON 結果（不是只看摘要），並由彙整者逐項回到原始碼核對；其中 4 個稽核探針與新增的 process-tree 探針在本次工作階段重新執行過（見 0.2；其餘探針的數字沿用稽核結果）。
>
> - 稽核基準：Rocky `main` @ `1812992`（2026-10-04），本機工作樹乾淨；OpenDots @ `c2569bb`（MIT）。
> - 路徑一律使用 repo 相對路徑；OpenDots 路徑加上 `opendots/` 前綴。審查期間的截圖寫成「審查截圖〈畫面〉」，探針腳本只寫用途（例如「claim 洩漏探針」）；它們都是審查期間的暫存檔，未提交進 Git，repo 中找不到。
> - 不收錄個人資料：證據檔中出現的本機路徑一律寫成「本機絕對路徑（含使用者名稱）」。
> - 本版已套用一輪逐句事實查核的更正，並與計畫的說法對齊；查核範圍、更正數量與計畫原 §1.9 的更正表都在第 6 節。審查期間 GitHub 上開著 11 個 PR，其狀態與處置見 0.4。
> - 對標研究：另一個工作階段的「Rocky 對標研究」提出的 Rocky 問題，已回到程式碼重新確認並新增為 D23–D27（第 2 節）；整合方式與兩邊看法不同之處見第 7 節。
> - 所有執行都在 Linux 雲端 sandbox；沒有在擁有者的 Windows 主機上執行任何東西，也沒有呼叫任何真實模型（live provider）。Linux 上的結果不能當成 Windows 結果。

**狀態標記**

| 標記           | 意義                                                           |
| -------------- | -------------------------------------------------------------- |
| 【已重現】     | 以實際執行程式重現（稽核者或彙整者執行的探針、建置或 UI 操作） |

### 0.3 限制

- 沒有任何真實模型憑證或 live provider 呼叫；涉及 provider 行為的缺陷（例如 cached tokens）只做到程式碼確認。
- 沒有在擁有者的 Windows 主機上執行；既有證據 75 筆 AT 中有 73 筆只在 Windows。
- Playwright e2e 套件本次沒有執行；UI 結論來自實際啟動後的截圖與 DOM 量測。
- 第三方 MCP server 只用 MCP TypeScript SDK 的 in-memory server 測試，沒有連實際外部 server。
- 遠端有 11 個尚未合併的 PR：#1–#7 是 Dependabot、#9 是 Dependabot 分組設定、#8 修 CI（另含 data root 正規化）、#10 是 UI 首次設定與視覺重設計、#11 整合 #1–#7、#9 與 #8；所有發現以本機 `main` @ `1812992` 為準，各 PR 的處置見計畫 P0.0 與 O19，以及本附錄 0.4。

## 2. 已驗證的缺陷

本節收錄影響行為的缺陷，另附一項測試判定問題（D20）與一項隱私問題（D21）。每一項都由彙整者回到引用的程式碼確認過；claim 洩漏探針、schema 探針、MCP SDK server 探針、遮蔽探針 與 process-tree 探針已在本次重跑，RPC 逾時探針、查詢計畫探針 的數字來自稽核者的執行（見 0.2）。文中提到的探針與截圖都是審查期間在暫存區執行或產生的檔案，未提交進 Git。

### D1【已重現】正式建置不含 agent-worker，README 的 `npm run build && npm start` 無法執行任何 Work（嚴重）

- 證據：`tsconfig.build.json:9-15` 的 `include` 只有 `apps/daemon`、`packages`、`fixtures`、`scripts/evaluate.ts`、`scripts/data-command.ts`；`apps/daemon/src/work-service.ts:1551-1557` 在 dist 模式下 fork `../../agent-worker/src/main.js`；建置後 `dist/apps/` 只有 `daemon/`。`README.md:24-29` 的 Quick start 正是 `npm ci → npm run build → npm run doctor → npm start`。`scripts/repo-guards.mjs:109-126` 的「必要 runtime 檔案」清單也漏了 worker。
- 重現：`npm run build` 後執行 `node dist/apps/daemon/src/main.js`，送出合成 Work，約 80 ms 後狀態變成「失敗」，訊息 `Worker process stopped before Agent result`（事件 `rocky.worker.interrupted`、exitCode 1）。同一情境改用 TS 原始碼啟動則正常完成。見審查截圖〈正式建置・決定後〉。
- 為何沒被抓到：所有測試與 e2e 都經 tsx 從原始碼啟動；`playwright.production.config.ts:22` → `tests/e2e/dev.mjs` → `scripts/dev.mjs` 也是原始碼；CI（`.github/workflows/verify.yml:44`）只建置，從不啟動建置結果。
- 影響：照文件安裝的使用者，核心功能完全不能用。
- 建議：把 worker 納入建置，並讓建置在缺少預期輸出時失敗；新增「`npm run build && npm start` + 完成一個 fixture Work」的 smoke 測試。這應該是重構的第一步，作為搬檔案時的安全網。

### D2【已重現】Worker RPC 固定 30 s timeout，任何超過 30 s 的模型或工具呼叫都會讓整個 run 失敗（嚴重）

- 證據：`apps/daemon/src/worker-channel.ts:436-439` 對每個 worker request 設 `setTimeout(() => abort.abort(new Error("Worker request timeout")), 30000)`，沒有依進度重設；`:463-466` 以 `Promise.race` 與 abort 競賽；失敗時 `:475-489` 只回傳通用的 `worker_request_failed`。`apps/daemon/src/work-service.ts:1600-1605` 處理 `tool_request` 時**沒有**把 request signal 傳給 `hooks.call`；`:1606-1611` 的 30 s 還包含等待 model slot 的時間。對照 `packages/agent-runtime/src/configured-model.ts:202`（預設 request timeout 120,000 ms）、`:390`（first token 60,000 ms）、`packages/contracts/src/models.ts:55-57`（最多 600,000 ms）、`packages/contracts/src/native-command.ts:8`（命令 timeout 最多 300,000 ms）。
- 重現：稽核者的 RPC 逾時探針使用真正的 `WorkerChannel` 與 `apps/agent-worker/src/main.ts`（configured 模式），讓 handler 延遲 `model_request`：延遲 2,000 ms 時 3,294 ms 正常完成；延遲 31,000 ms 時在 31,232 ms 被拒絕，錯誤只是 `Agent worker invocation failed`，handler 的 signal 在 31,215 ms 被 abort，`channel.error === null`。`tests/worker-channel.test.ts` 沒有慢請求案例。
- 影響：較慢或本機模型、長輸出、排隊等待 model slot，都會讓 run 失敗，且使用者設定的 deadline 被默默覆蓋。已核准的命令若超過 30 s，agent 會收到「失敗」，但 daemon 端的命令仍在執行並稍後 settle，agent 的認知與帳本不一致；模型若因此重試，可能造成重複副作用（此後果【未確認】）。
- 建議：立即修正（與重構無關）：移除 `model_request` 與已核准工具執行的固定計時器，改用各自的 deadline（命令 `timeoutMs` 加寬限期），並把 request signal 傳進 `hooks.call`；以 fake timers 加 >30 s 的回歸測試。

### D3【已重現】一次失敗的命令或 MCP 錯誤會永久鎖住目標，之後所有 Work 都無法在該 workspace 執行命令（嚴重）

- 證據：`apps/daemon/src/workspace-command-dispatch.ts:144-169` 只有 `exit 0` 算 `succeeded`，任何已啟動但非 0 的結束都 settle 為 `unknown` 並丟出 `unknown_effect`；`apps/daemon/src/workspace-commands.ts:111-115` 原生命令的 claim key 是**整個 workspace**；`apps/daemon/src/operation-ledger.ts:485-493` 在 dispatch 時插入 `target_claims`，衝突即 `target_busy`；`:515-518` 只有 outcome 不是 `unknown` 時才刪除 claim；`apps/daemon/src/operation-reconciler.ts:125-128` 也只在已知結果時釋放；`apps/daemon/src/native-command-receipts.ts:160-164` 的觀察者同樣把非 0 結束對應為 `unknown`；`apps/daemon/src/work-service.ts:1510-1513`、`:1528-1535` 對 MCP `isError` 也 settle 為 `unknown`，而 MCP 的 claim key 是工具身分（`:1383`、`:2722-2729`）。`tests/workspace-command-dispatch.test.ts:150-155` 把「非 0 → unknown」寫成預期行為。
- 重現（本次重跑 claim 洩漏探針，Node 24.12.0）：
  - 第一個 Work 執行 `exit 1` → 丟出 `Command did not finish successfully; inspect effects before retrying`，phase/outcome = `settled/unknown`，`target_claims` = 1。
  - 執行對帳 → 觀察結果 `unknown`，對帳結果 `unknown`，`target_claims` 仍為 1。
  - **另一個新的 Work** 在同一 workspace 執行 `exit 0` → `Target has an active or unreconciled operation`，停在 `authorized/not_executed`。
- 影響：coding agent 的核心循環「跑測試 → 修 → 再跑測試」在第一次紅燈後就死掉：目前 Work 變 `blocked`、retry 被拒（`operation-ledger.ts:103-114`），之後該 workspace 的所有原生命令永久 `target_busy`，沒有任何 API 可以釋放。`workspace_write` 若 publish 後確認失敗，也會永久鎖住該檔案路徑（`canReconcile` 不包含它）。

### D20【已重現；判定為環境／測試問題，非產品缺陷】`tests/terminate-process-tree.test.ts:47` 在稽核用的 Linux sandbox 失敗

- 證據：`apps/daemon/src/terminate-process-tree.ts` 在 POSIX 以 `process.kill(-pid, 'SIGKILL')` 殺整個 process group；測試以 `process.kill(descendant, 0)` 判斷後代是否存活，`expect.poll` 預設約 1 s 期限。
- 重現（本次新增探針，重跑 5 次）：後代確實被殺，但成為 zombie（`/proc/<pid>/stat` 狀態 `Z`、父行程 1）；這個 sandbox 的 PID 1 是 `process_api`（Firecracker init），收割 zombie 需要約 1.0–1.9 s（彙整時量得 1,001–1,019 ms；事實查核時以 5 ms 輪詢重跑 5 次為 1,274–1,929 ms），期間 `kill(pid, 0)` 仍然成功，所以超過 1 s 的 poll 期限；約 2 s 後後代都已消失。
- 結論：`terminateProcessTree` 的行為正確；失敗來自「zombie 也被視為存活」加上 PID 1 收割較慢。建議測試改為檢查 `/proc` 狀態（或在 Linux 放寬期限），避免 CI 誤報。

## 4. 值得保留的優點

重構的目標是改結構，不是丟掉這些已經做對的事。

### 4.1 安全核心（即使只在本機也有正當性）

- **Daemon 是唯一權威**：worker 不會拿到 `domain.sqlite` 路徑、環境變數只保留 PATH/SystemRoot/TEMP/TMP，只能透過型別化 RPC 取得模型與工具（`apps/daemon/src/worker-channel.ts:46`、`:129-133`；spec:273-276）；但 worker 與 daemon 是同一個 OS 使用者，這不是 OS sandbox（spec:276）。每個有副作用的 agent 工具都只是 `hooks.call` 的薄 proxy（`packages/agent-runtime/src/factory.ts:223-458`）。
- **精確核准綁定**：核准記錄 `operationId = runId:callId` 與 fingerprint，interrupt 以 args hash 綁定到唯一一個 root tool call（`work-service.ts:2641-2652`），執行時重新推導並比對 fingerprint（`policy.ts:82-91`、`work-service.ts:2153-2158`、`:2915-2923`、`:2930-2940`）。這是最核心的安全性質，必須保留。
- **不自動重播**：重啟時 running/waiting 的 Work 變為 blocked、未派送的操作 settle 為 `not_executed`（`work-service.ts:234-248`、`operation-ledger.ts:203-258`）；phase/outcome 轉移表精簡且 CAS 正確（`operation-ledger.ts:442-460`、`:495-514`）。保留概念、簡化 enum。注意：值得保留的性質是「已派送、結果未知的副作用永不重播」；重啟時把 `waiting_approval`（工具尚未派送）的 Work 一律變成 `blocked` 正是缺陷 D13，計畫在 O3(c) 把它反轉為從 checkpoint 續跑。
- **原子檔案寫入**：`O_EXCL|O_NOFOLLOW` 暫存檔、fsync、保留 mode、rename 或 link（新檔不覆蓋中途出現的檔案）、發布後 hash 驗證（`workspace-writes.ts:78-158`），prepare 時的 expected-hash 前置條件（`:49-58`）。
- **路徑包含**：每個路徑段都拒絕 symlink，並有敏感路徑黑名單（`.git`、`.ssh`、`.env*`、sqlite、browser-profiles、credentials），也拒絕檔案系統根、家目錄與 Rocky 資料目錄（`file-target.ts:47-160`、`workspaces.ts:37-48`、`:71-97`）。
- **子行程衛生**：`shell=false`、絕對路徑執行檔、不解析 PATH、env allowlist 讓 provider 金鑰與 `NODE_OPTIONS` 不會流入子行程、輸出上限與 timeout、detached group + 整棵樹 kill（`native-environment.ts:9-14`、`:49-70`、`:101-125`；`terminate-process-tree.ts`）。
- **Git 強化**：`core.hooksPath=/dev/null`、`GIT_CONFIG_NOSYSTEM/GLOBAL`、無 fsmonitor、無 prompt、拒絕 filter driver（`git-worktree.ts:58-80`、`:250-255`）。
- **DB 內副作用在同一 transaction 內 settle**：memory/document 寫入與操作 settle 同一個 SQLite transaction（`work-service.ts:2086-2099`），應成為 `transactional` EffectKind 旗標。
- **串流秘密遮蔽**：保留尾端視窗，跨 SSE frame 分割的憑證也不會外洩（`redaction.ts:5-29`）。
- **Localhost 強化**：綁 127.0.0.1（`main.ts:22`）、Host allowlist 防 DNS rebinding、Origin allowlist + 自訂 header 防 CSRF（`http.ts:58-81`）、CSP 與 nosniff（`:50-57`）；下載以 sandbox CSP 與 attachment disposition 提供（`:356-367`、`:397-411`、`:582-594`）；Vite dev server 也綁 127.0.0.1 並設 CSP（`apps/web/vite.config.ts:7-15`）。
- **憑證不落地**：模型與 MCP 設定只存環境變數名稱，公開 DTO 只回報 configured/available（`packages/contracts/src/models.ts:46`、`:60`、`:103-115`；`model-registry.ts:146-157`）；endpoint 不得含憑證、query 或 fragment（`models.ts:5-28`）；MCP 設定拒絕疑似秘密的 env 名稱與 CLI 參數，header 值只能以環境變數參照提供，並拒絕 protocol／session header（`packages/contracts/src/mcp-config.ts:5-11`、`:19-25`、`:64-78`）。
- **拒絕 redirect + 精確 endpoint**：bearer token 不會被送到 redirect 目標（`packages/agent-runtime/src/model-network.ts:121-137`、`configured-fetch.ts:17-21`、`:40`、`mcp-manager.ts:329`）。
- **MCP 與工具輸出視為不受信任資料**：resource link 不解參照、inline 圖片以 magic bytes 與尺寸驗證、prompt role 被引用而非提升（`packages/agent-runtime/src/mcp-result.ts:22-232`）；stdio server 無 shell、獨立 process group 並確認整棵樹已結束（`owned-stdio-transport.ts:52-59`、`:99-130`）；stdio 訊息與 HTTP 回應各 2 MiB 上限（`mcp-manager.ts:303`、`:348-379`），discovery 的頁數、工具數、位元組與 cursor 迴圈上限（`:480-507`）。
- **HTML 預覽縱深防禦**：parse5 allowlist + CSP meta（`html-preview.ts`）與 `sandbox=""` 的 srcdoc iframe（`apps/web/src/artifacts.tsx:264-271`）。
- **圖片解碼隔離**：在 `worker_threads` 中以 `resourceLimits` 與 10 s 期限解碼，只重新編碼像素並去除 metadata（`attachments.ts:147-199`、`attachment-codec.mjs`）。
- **Backup/restore**：SQLite online backup API、writer lock、checksummed manifest、symlink-safe IO；還原時阻擋進行中的 Work、使核准過期、撤銷授權並停用自動化（`backup.ts:440-463`）。
- **遙測全關**：`packages/agent-runtime/src/environment.ts:1-7` 在 import 最前面關閉 CopilotKit、Scarf、Promptfoo、LangSmith 遙測；`scripts/network-audit.mjs` 以 `diagnostics_channel` 記錄非 loopback 的 HTTP／undici 請求（目前只掛在 `npm run test:network` 執行 `scripts/evaluate.ts` 時，`package.json:72`），是便宜且誠實的「沒有隱藏出站」證據。OpenDots 沒有關閉 CopilotKit 遙測。
- **Scratch 路徑政策**：驗證 canonical 絕對 `/scratch` 路徑並限制 glob 巢狀，對應一個未修補的上游問題（`packages/agent-runtime/src/scratch-policy.ts:32-50`（路徑）、`:54-75`（glob 巢狀預算））。
- **串流結尾不視為成功**：要求明確的終止符與 finish reason，並檢查 tool call 一致性（`packages/agent-runtime/src/model-stream.ts:174-190`），應成為替換 adapter 時的 parity 測試。

### 4.2 持久化與即時資料

- 一個 SQLite domain DB + WAL + 單一寫入者 daemon lock，是本機應用正確的持久化模型（`store.ts:77-92`、`writer-lock.ts`）；巢狀 transaction 防護與 `BEGIN IMMEDIATE`（`store.ts:406-427`）；Work 的 revision CAS（`store.ts:460-505`）。
- Snapshot + cursor，再接 SSE 與 `Last-Event-ID` 續傳，是正確的重連模型（`http.ts:704-735`、`store.ts:630-690`）。前端 `rocky-adapter.ts:62-63`、`:138-265` 是單一 snapshot+SSE 擁有者，有 generation guard、重連後重新取 snapshot、離線/上線處理、只讓 revision 前進的合併；明顯優於 OpenDots 的 6 個 3–4 秒輪詢迴圈。
- Routine 的 occurrence ID 是決定性的，並有明確的 misfire 政策（skip 或 coalesce-one），漏掉或重複的 tick 不會重複送出（`routines.ts:17-22`、`:181-216`、`:240-250`）。
- 文件以 `expectedRevision` + `UPDATE ... WHERE revision=?` 與內容定址 blob 實作樂觀並行（`documents.ts:270-317`），與 `opendots/src/server/pages.ts:165-199` 同一模式；artifact 發布綁定已確認的 `workspace_write` 收據，每次讀取都驗證 blob（`artifacts.ts:59-94`、`:136-150`）。
- `ModelSlots` 是小而有測試的優先序 semaphore，等待時不佔 slot（`model-slots.ts:10-62`）；admission 限制以 zod 驗證並有上界（`admission-config.ts:3-22`）。
- `diagnostics.ts:6-64` 明確排除訊息、參數、路徑與憑證，大小適中。

### 4.3 Runtime

- Deep Agents 以原生方式使用而非包裝：`StateBackend` 虛擬檔案系統（預設拒絕、只有 `/scratch` 可寫）、唯讀 `/skills` `CompositeBackend`、原生 summarization middleware、一個短暫的 general-purpose 子代理（工具集縮減、唯讀、有自己的 guard），符合「native tasks are ephemeral children」（`factory.ts:463-471`、`:528-551`、`:617-643`）。
- Policy guard 以 `AsyncLocalStorage` 帶上父呼叫祖先，發出 started/completed/failed/denied 結構化事件，能乾淨地歸屬子代理的工具呼叫（`factory.ts:111`、`:168-218`）。

- Provider 錯誤在離開網路層之前就被遮蔽（`model-network.ts:140-148`、`configured-fetch.ts:50-56`）。
