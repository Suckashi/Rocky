# Owned native steering

Source1350956; T-012/T-019 contribution. POST `/api/v1/works/:id/steer` validates the exact current run, execution session and revision. A stable request UUID plus canonical intent returns the durable receipt on retry; changed content returns409. Normal running/waiting-approval Work can accept at most8 pending corrections. Accepted is not applied, tool permission, effect success or Work completion.

The root-only native middleware reads corrections at its next beforeModel boundary and appends identified Human messages. Before the next model RPC, the worker supplies the official saved checkpoint identity. The daemon checks exact message ID/text in that owned run checkpoint, rechecks current ownership, then atomically writes applied receipt, visible immutable history and domain event. Natural Work revision changes after acceptance do not retarget the original run/session. Native child execution does not consume the correction into its own message history.

If Work terminates or is stopped before confirmed application, pending receipts become not_applied in the Work lifecycle transaction. Accepted/not_applied corrections never create ghost user-history messages. The UI uses the existing shared event projection; an expanded Work detail lazily loads receipts without an extra polling owner. It labels the three states separately and explains that an in-flight model/tool is not revoked: use exact Stop for immediate cancellation. Steering while waiting approval waits for a subsequent model boundary and never grants or revokes approval itself.

Windows tests use actual native workers/checkpoints with a configured loopback provider fixture: held request, root todo boundary, native child boundary, independent background completion, target/idempotency rejection, terminal-before-boundary and Stop. Browser checks submit through the actual UI, observe accepted→applied, reload at390px and verify no page horizontal overflow.
