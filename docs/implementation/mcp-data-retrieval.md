Root-only mcp_data retrieves an explicitly discovered resource, URI template or prompt through the configured daemon-owned MCP connection. Native interrupt, exact intent fingerprint, daemon decision validation, operation authorization/dispatch/receipt and cancellation use the same pipeline as mcp_call. Children, fixture/reflection/evaluation modes cannot use this route. No separate runtime, service polling or automatic resource-link fetch is introduced.

The manager requires the current cached data catalog and registry/configuration identity. Static URI and template/name must exist in that catalog. Template variables are bounded and checked against the SDK UriTemplate variable names before SDK encoding/expansion; prompt arguments must match discovered names and required fields. Metadata, target, arguments and expanded URI bind the fingerprint. Owner approval cards use the existing PageReviewCard-derived structure, with readable action, server, daemon-generated expanded URI or prompt name, collapsible exact arguments and approval/rejection. A changed connection/catalog revokes execution. Retry comparison ignores a reconnected registryRevision while retaining the target and arguments, so reconnect cannot authorize repeating an unknown effect.

Daemon dispatch uses SDK readResource/getPrompt and sends rocky/operation metadata for future receipt correlation. Responses remain tool task data. Prompt roles are quoted text labels, never system/human/assistant graph messages; resource text uses embedded-resource blocks. PNG/JPEG resources and prompt image blocks follow existing typed media validation and explicit default-off model vision settings. Unsupported blobs remain uninspected artifacts. No image base64 is copied into structured model text. Post-dispatch errors remain unknown and Work is blocked; a protocol response is not proof of a remote job finishing.
