# Explicit retry as a new Work

Source c533a58; T-013/T-019 contribution. POST `/api/v1/works/:id/retry` requires a new stable requestId plus exact source run/session/revision and confirmed effectRefs. It accepts an inactive normal Work, preserves its immutable prompt/mode/kind/workspace/budget configuration, and creates new Work, Run, ExecutionSession and budget rows with retryOf. An explicitly selected runnable model revision can replace a stale configured selection. No original Work is reset or graph invocation restarted. Repeated identical commands return the same new Work across daemon restart; changed request intent returns409.

The daemon reviews the source and its retry ancestry. Any unknown/dispatched effect blocks retry, including when a client supplies a purported confirmation. Known succeeded/no-effect outcomes require exact operation revisions, plus the actual reconciliation receipt identity where applicable. A client cannot submit an outcome. GET retry-review exposes these authoritative summaries for UI confirmation; POST revalidates them. Pending/not-executed effects confer no permission.

Prior outcome/result receipts enter the new owned checkpoint context as evidence only. Background retries receive their own ancestor evidence, without inheriting main history or the unrelated background inbox. Normal main context can still come from a safe completed main checkpoint; pending graph tasks/interrupts/effects are not copied. Ancestry is capped at128, review at1000 operations and command at100 confirmed effects; excessive history fails explicitly.

Operation preparation checks retry ancestry before preparing another effect. A confirmed succeeded operation with the same tool and canonical argument hash cannot be repeated under a new callId/run. New rows record the argument hash; prior Rocky rows can derive it from their matching saved approval. When prior intent cannot be determined, repeating that tool is denied. A distinct new intent still requires fresh ordinary approval. Known-no-effect retries can request a new approval; no approval/grant is copied. The current guard covers Rocky's implemented synthetic effect ledger; future configured MCP/workspace adapters must bind connector and actual target identity as well.

UI presents retry within existing collapsed Work details, explains effects and requires explicit review. It uses shared events and lazy reads, with a stable request UUID across ambiguous submission failures. The new card says it is a new retry execution; raw source IDs remain deeper evidence. Existing neutral OpenDots-aligned presentation tokens and focus styles are reused. There is no fake success, separate event stream or polling loop.

Actual Windows tests use native child workers and a configured loopback provider. They prove new identities/budget, source immutability, restart idempotency, unknown denial, exact reconciliation refs, ancestor receipt delivery, denial-before-preparation of a repeated succeeded effect and fresh approval after confirmed no-effect. Browser checks actual API/UI at1440x900 and320x844, including reload, keyboard confirmation, no horizontal overflow and focused create control above composer. These fixtures do not prove external business effects or live provider quality.
